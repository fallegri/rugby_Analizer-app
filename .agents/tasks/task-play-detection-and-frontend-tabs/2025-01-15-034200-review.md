# Rugby play detection engine and tabbed frontend layout

Adds a heuristic-based rugby play detection system that identifies tackles, scrums, rucks, line-outs, and trys from player movement patterns (speed, proximity, clustering duration). Detected plays are optionally enriched with AI-generated tactical explanations via the existing provider abstraction. The frontend AnalysisPage is reorganized from a 2-column grid into a sidebar-tabbed layout with five sections (Video, Analisis, Metricas, Jugadas, IA Chat), and a new PlaysTimeline component renders detected plays as color-coded expandable cards.

Watch for: **Position data contract mismatch** between backend (serializes `[x, y]` array) and frontend TypeScript type (`{x: number, y: number}` object) — currently benign because the UI doesn't render position, but will break on first use (confirmed). **O(n³) tackle detection** on large datasets — linear-scan `_get_point_at_time` inside player-pairs × timestamps loops (confirmed). **Module-level singleton state** in the plays router means detected plays persist across requests in-process but vanish on restart with no indication to the client (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The tackle detection path has quadratic-times-linear complexity that will degrade on real match-length data (30 players × 900+ timestamps × linear route scans per lookup). Scrums, rucks, and line-outs share a common sliding-window cluster method that avoids the pairwise blowup.

The service layer calls AI for each detected play in sequence. AI failures are handled gracefully per-play, and unconfigured providers are skipped entirely. Serial enrichment means latency scales linearly with detected play count — acceptable for a handful of plays but noticeable with dozens.

The API layer stores detected plays in a module-level dict (`_detected_plays`) with no persistence across restarts, no eviction, and unbounded growth. The existing analysis routes use `AnalysisService` with managed state via `app.state`, so this is a departure from the established pattern.

The frontend type `DetectedPlay.position` is `{ x: number; y: number }` but the backend serializes position as a flat `[x, y]` list. The mismatch doesn't crash today because `PlaysTimeline` never reads `position`, but any future use (field highlighting on click) will encounter a runtime type error.

The frontend refactor moves to a sidebar + content-area pattern with component-local tab state. Switching away from AnalysisPage and back resets the active tab to "Video", losing the user's navigation context.

1. **Position data contract mismatch** — Backend serializes `position` as `[x, y]` (a JSON array), frontend types it as `{x: number, y: number}`. Fix by changing `_play_to_dict` to emit `{"x": play.position[0], "y": play.position[1]}` or change the frontend type to `[number, number]`.

3. **Unbounded in-memory play storage** — `_detected_plays` module-level dict grows without limit and has no eviction. Move storage into `app.state` or add an LRU/TTL eviction strategy consistent with how analysis results are managed.
4. **Serial AI enrichment** — Each detected play's AI call runs sequentially. For matches with many detected events, use `asyncio.gather` with a concurrency limiter to parallelize.
5. **Ruck/scrum overlap** — Independent detection passes can emit both a ruck and a scrum for the same physical event when a cluster grows past the ruck threshold into scrum territory. Cross-type deduplication is absent.

## Position contract mismatch between backend and frontend

The service's `_play_to_dict` method converts the tuple position to a Python list:

```python
"position": list(play.position),  # yields [50.0, 35.0]
```

The frontend interface declares:

```typescript
position: { x: number; y: number };
```

These are incompatible JSON shapes. The type annotation is lying to TypeScript — any component that accesses `play.position.x` will get `undefined` instead of a number. The fix belongs on the backend side (emit an object with `x` and `y` keys) since the frontend type is the more ergonomic shape for UI consumption.

## Tackle detection performance characteristics

The tackle detection path executes:

```
for each pair of players:              O(n²/2)
  for each common timestamp:           O(T)
    _get_point_at_time(route, t):      O(R) linear scan
    _check_convergence(route_a, ...):  O(R) linear scan × 2
```

For 30 players tracked at 30 fps over 30 seconds: 435 pairs × 900 timestamps × ~900 route entries = ~350 million comparisons in the inner loop. This is a blocking `async` endpoint with no background offloading — the event loop is starved for the full computation duration.

Building a `dict[float, dict]` index per route at the start of detection (a one-time O(n) pass per player) would reduce `_get_point_at_time` to O(1) and eliminate the cubic blowup. Even with subsampled route data from the existing pipeline, the quadratic pair × timestamp outer loop remains expensive without the index.

## Module-level state in the plays router

```python
_detected_plays: dict[str, list[dict[str, Any]]] = {}
_play_detection_service = PlayDetectionService()
```

The dict accumulates entries for every session that runs play detection and never releases them — a memory leak in a long-running process. The existing `AnalysisService` pattern uses `app.state` with proper lifecycle management; the plays router should follow the same pattern.

The `GET /plays` endpoint returns 404 after a server restart even if the analysis data still exists. The client cannot distinguish "never detected" from "server lost state." The error message instructs the user to re-run detection without explaining why results vanished.

## Ruck and scrum overlap on growing clusters

`_find_largest_cluster` uses a greedy single-center approach. If a cluster of 10 players exists, the scrum detector finds it (≥8). But a subgroup of 4–6 within that same cluster satisfies the ruck detector independently because ruck detection runs as a separate pass over the same data. Since deduplication only compares plays of the same `play_type`, a single physical event (a ruck growing into a larger contest) can emit both play types for overlapping time ranges.

A post-detection pass that suppresses lower-confidence cross-type overlaps within the same time window and spatial region would address this.

## Frontend tab state loss on remount

The active tab (`useState<TabId>('video')`) resets every time the component remounts. Navigating away from `/analysis/:videoId` and back returns the user to the Video tab regardless of where they were. Moving `activeTab` into the Zustand store would preserve context.

The sidebar renders all tabs regardless of analysis state with no disabled/badge indication. Tabs like "Metricas" and "Jugadas" show empty states before processing completes, which is functional but provides no at-a-glance signal of which tabs have content.

## Test coverage gaps

Not tested in the backend: `_check_convergence` fallback behavior (returns `True` when no earlier point exists) — verified only implicitly through tackle tests, making regressions hard to trace.

Not tested in the frontend: the `handleDetectPlays` async flow (API call → store update → re-render), error state rendering, and disabled button behavior when `sessionId` is null. The mock wires up `detectPlays` but never asserts it was called or verifies state transitions through the async path.
